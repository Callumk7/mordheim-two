Structured `useLiveQuery` usage and `ssr: false` with all source collections preloaded are appropriate (`src/routes/events.tsx:6-16`).
- **Correct:** The database migration and Drizzle schema agree, with foreign keys for the match and both warbands (`src/db/schema.ts:48-61`, `drizzle/0004_simple_wild_pack.sql:1-12`).
- **Correct:** Creation defaults are separated from `EventUpdateSchema`, avoiding defaults being injected into partial updates (`src/db/event.ts:3-17`).

- **Blocker:** Cascading parent deletion leaves the Events TanStack DB collection stale. The database cascades when a match or warband is deleted (`src/db/schema.ts:52-58`), but the parent collection handlers only refetch their own collections (`src/db-collections/matches.ts:40-46`, `src/db-collections/warbands.ts:46-52`). `collection.preload()` merely reuses an already-started preload, so returning to Events does not guarantee a refresh (`src/routes/events.tsx:8-13`; TanStack DB `collection/sync.ts:518-523`). Reproduction: load Events, delete a referenced match or warband, then return to Events. The deleted database rows can remain visible as “Unknown match/warband” (`src/routes/events.index.tsx:82-91`), and the detail loader treats the stale row as existing (`src/routes/events.$eventId.tsx:10-14`). After the parent transaction persists, explicitly refetch/invalidate `["events"]` before navigation in both deletion flows (`src/routes/matches.$matchId.delete.tsx:63-65`, `src/routes/warbands.$warbandId.delete.tsx:63-65`), or otherwise coordinate the cross-collection cascade centrally.

- **Blocker:** Self-referential events are accepted and actively produced when only one warband exists. The new page renders with one warband and defaults both attacker and defender to it (`src/routes/events.new.tsx:49-55`); the form only checks that IDs are non-empty (`src/components/event-form.tsx:27-30`), while neither Zod nor SQLite enforces different IDs (`src/db/event.ts:3-17`, `src/db/schema.ts:53-58`). If attacker and defender represent opposing warbands, require two warbands, reject equal IDs in the UI/server, and add a database check constraint. The database constraint is important because partial updates cannot reliably validate the invariant without loading and merging the existing row.
